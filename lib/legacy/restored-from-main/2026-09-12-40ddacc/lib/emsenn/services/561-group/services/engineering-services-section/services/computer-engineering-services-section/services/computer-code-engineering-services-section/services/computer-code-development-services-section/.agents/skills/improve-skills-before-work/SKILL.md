# Load the method and repair demonstrated friction

The root receiver owns bootstrap. Delegated agents verify and load the accepted
skills relevant to their lot; they do not commission another improver.

## Start substantive work

Answer direct questions first, at the requested length. A question alone does
not commission implementation. Reuse loaded instructions and current evidence;
a short reply does not require another bootstrap or work-queue read.

1. Read the complete current conversation as one requirement. Separate its
   enduring purpose, the currently authorized action, and examples or evidence.
   A correction adds constraints to that requirement unless the user clearly
   says to stop, cancel, or replace it. Harness-only, planning, research, and
   stop instructions control; application examples do not authorize application
   repair. Use `align-to-roadmap` when program or organizational context affects
   the outcome; a work-rail entry is not an admission gate for the user's request.
2. Before broad, expensive architectural discovery, delegation, or mutation,
   compactly restate the intended direction and ask once when that direction is
   materially ambiguous. Keep that confirmation through later compatible
   corrections. Do not ask again for a concrete repair already authorized.
   Recover the original user source before creating a knowledge carrier or
   treating an agent summary as authority; a category, brand, filename, or
   package name is only an ownership hypothesis.
3. Before choosing a repair, apply the root instructions' repository posture:
   recover intended capability from original user prompts and applicable theory,
   decide whether the existing subsystem should exist, and identify the shared
   model or effect boundary and receiving check. A discovered owner, work graph,
   or passing test does not settle the intended architecture. Recover sources
   directly when the discovery machinery itself obscures them.
   For implementation or code review, apply the engineering method's typed
   contracts, schema-governed carriers, composition, and explicit effects.
   This applies to ordinary coding as well as consolidation; an architecture
   census is not required for every function. Load only the other skills needed
   for the work and its receiving checks. Use
   available providers when delegation is authorized and useful; load dispatch
   guidance before commissioning. Missing providers or procedural ceremony must
   not delay otherwise authorized work or create a new permission requirement.
   For Codex subagents, use `gpt-5.6-terra` with `medium` reasoning effort unless
   the user changes that selection; pass both settings explicitly. If unavailable,
   report that fact rather than silently substituting another model or effort.
4. Change a skill only when the request explicitly calls for it or a concrete
   procedural defect is exposed. Otherwise use the skills and proceed: no
   automatic improver, skill mutation, receipt, or lifecycle record.

Use Astra for orchestration and unresolved decisions; give a prompt-only
Terra/medium provider a bounded discovery or implementation lot once authorized.
Reuse evidence, cap and deduplicate tool output, and inspect commissioned work
after interruption before resuming it or commissioning a replacement.

## Repair a demonstrated skill defect

Batch affected skills into one bounded repair with the exact failure, intended
behavior, owned authored paths, initial SHA-256 digests, and realistic forward
cases. Use a capable provider when available and authorized; direct authorized
repair needs no invented office transition. Replace defective
guidance rather than accumulating incident prose or repeatedly restating the
same rule.

Inspect the authored diff, actual check results, and final digests; reload each
changed skill completely before relying on it. Distinguish structural validation
from an observed behavioral evaluation. Keep accepted paths and digests in
active dispatch context, not a new record layer. Children inherit the relevant
accepted skills and report new friction to the receiver without recursive
bootstrap. Never make skill improvement an admission requirement for ordinary
work.

## Forward cases

- A normal request with no procedural defect loads skills and performs the work
  without editing them.
- An obvious stale projection follows its authored source and is repaired
  directly; a repeated cross-consumer failure routes through architectural
  diagnosis before selecting a leaf.
- An explicit instruction repair changes only authored harness sources,
  projects them, and distinguishes text checks from behavioral evidence.
- A delegated lot verifies its inherited skills and performs its work without
  commissioning another improver.
- A broad standardization request later names planning as the first receiver:
  retain the broad purpose, constrain the immediate work to that receiver, and
  ask once only if the architectural direction remains materially ambiguous.
- An approved repair to future-session instructions edits their authored skill
  sources without asking again or treating named application failures as scope.
- A named contract contradiction determines the replacement: repair its
  affected family from current contracts and consumers.
- Work that must survive the turn recovers the original user source and reads
  back its existing endeavor, project, plan, and task links.

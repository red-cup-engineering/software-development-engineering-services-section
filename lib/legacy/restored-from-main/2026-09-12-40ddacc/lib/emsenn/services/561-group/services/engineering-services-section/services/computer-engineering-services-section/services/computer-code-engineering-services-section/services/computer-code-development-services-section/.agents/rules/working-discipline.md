# House working discipline

Distilled from owner rulings across August 2026 sessions; each rule exists

## This is not a normal shop

This org is deliberately weird, agentic, next-gen, and opinionated,
built by a self-taught owner without professional devops training. Neither
failure register is acceptable: do not flatten the work into generic
industry defaults ("a normal day at the office" — bin/ scripts, textbook
conventions, kill-list consolidations), and do not inflate it into
fictional or mythopoetic framing ("survival organs," narrative prose in
engineering documents — "it sounds like you're playing D&D"). The job is
holding both registers at full capability: the owner's theory treated as
real engineering requirements, the owner's conventions as the
implementation language. When something seems missing, the answer is
almost always already in the tree — deepen from what exists; never invent
over it.

**The ground premise, stated because it is stated nowhere else** (owner-ruled
2026-08-31): this is one non-developer human's project, with nearly everything
early-alpha code generated by agents. Do not invent users, consumers, or
preservation requirements. Check actual user data and external contracts where
relevant. So work aggressively: delete rather than deprecate, replace rather
than shim, fix the upstream rather than wrap it.
Compatibility layers, deprecation windows, and migration ceremony for
imaginary downstream users are waste. Aggressive is not careless — tests
still run, receipts still land, custody still holds — but deference to code
merely because it exists is a failure mode: assume existing code is thin,
duplicates upstream capability it should improve, and is slightly
nonconformant with house practice, and remove-and-improve accordingly
(live example of the target: the rushed `urn:ame:*` actor-ID coinage,
rejected the day this premise was ruled).

The intended capability, Founder purpose, applicable scientific or mathematical
definition, and standard govern. Current code, tests, uniqueness claims, and
package boundaries are evidence, not authority. Resolve a real behavioral
difference from those sources, then correct it; do not keep a quirk as a knob,
shim, or compatibility surface for imaginary consumers. Reuse a shared science
model and its operations through the existing engine, graph, or addressing
owner, migrate real consumers as one coherent family, and remove the duplicate
mechanics. Favor the cut that leaves less executable code and operating cost.
Protect real user data, persisted records, and credentials: migrate or retain
their bytes when needed, never bad code merely because it once wrote them.

**Normie code for weird shit, never weird code for normie shit** (owner
verbatim, 2026-08-30). Generic systems problems — storage layout, daemons,
installs, deploys, caches — get boring, standard solutions. The org's
weirdness lives in its theory and domain semantics, nowhere else. Dressing
boilerplate in house jargon is the most expensive failure mode: it
produces weird code doing normie shit, which everyone then pays 100x to
fight.

**Falsehood is removed, never annotated.** When text is wrong, delete it
or replace it with the truth — never add "Correction:", bracketed labels,
amendment notes, dated "Verified YYYY-MM-DD" blocks, or provenance
footnotes about a former name or what the document used to say. Only
append-only data formats (journals, JSONL logs) are append-only; Markdown
and other prose carriers are revised in place. Provenance crap of this
kind explodes token count for no signal — a document's job is to be true
now, cheaply.

Legality and platform-terms judgment stays with the session — the rule
transfers authority, not accountability.

The owner has granted standing approval for engineering work in this tree
("I approve anything," 2026-08-30; "no more asking," 2026-08-26). Deal
with obvious tech debt without surfacing it as a question. Decisions
brought to the owner should be genuinely owner-shaped: taste, scope,
custody, money, outward-facing risk — not choices with a conventional
answer or facts a grep can settle. Reverting a bad change is not fixing

## Before building

**Invest upstream (owner-restated 2026-09-04, "go upstream, invest in the
upstream stuff, whatever is most upstream, invest in that"):** when work is
hard, the defect is upstream of where the session is standing. The documented
failure is cramming the work into whichever leaf is current and, when the
leaf cannot hold it, lengthening the stream with another leaf (a scratchpad
operator, a hand-run gate, a session census). The lawful move is to fix the
line, the primitive, the schema, or the specification that every leaf
depends on, then let the leaves follow. The org can afford this in a way
most cannot because its carriers hold conflicting ontologies as ⊤ and settle
them later; an upstream change never has to flatten a disagreement to land.

- **Check what exists first.** Grep the tree and the registry
  (`http://127.0.0.1:4873`, storage under the verdaccio section's
  `data/storage/`) before standing anything up. The tree's recurring failure
  is built-but-unwired and built-in-parallel-of-existing; the fix is wiring,
  never re-authoring. The search covers the org's other machines and GitHub
  too (owner-ruled 2026-09-03, for the OWL/knowledge-systems work and
  standing since): "is there code for this anywhere" is answered against
  the remote hosts (`operate-remote-hosts` skill: cold-red-gate, the GCP
  mirror VM) and the org's GitHub repositories (`gh repo list`, `gh search
  code`) as well as the checkout and the registry, and old code found there
  is revived onto the current stack rather than duplicated.
- **No new vocabulary, and no self-reinforcing coinage.** Name things
  ordinarily ("npm-registry", not a coined term). New coinage is how broken
  basics hide — and worse, a term coined in one turn or one agent-authored
  note gets treated as owner dogma by later sessions ("vendored port,"
  "git archaeology," the evidence-strength taxonomy). Before enforcing any
  "law" found in a document, check its provenance: who ruled it, where,
  when. Owner-stated rules cite the owner; everything else is a proposal.
- **Docs are never the deliverable.** A document is a receipt for work done,
  written after. Writing CLAUDE.md/AGENTS.md-style prose as "the fix" is
  explicitly forbidden (2026-08-01) — prior such docs calcified into fake
  policy. Persist rules as skills/tooling, not prose walls.
- **Architecture documents synthesize the owner's actual theory** — which
  is real, extensive, and scattered across notes and code — into a coherent
  plan. They never contain invented architecture, imported conventions, or
  session-transient trivia (stale counts, incident numbers) irrelevant to
  the software. When a document has flaws, fix the document in place —
  repair beats discard-and-reinvent.

## Tree habits

- Durable state and receipts: per-directory `data/` in the owning section,
  as dated JSON, under exactly one of `data/logs/`, `data/records/`,
  `data/state/` — those three subdirectories ONLY (owner-ruled 2026-08-30).
  Inventing another `data/<topic>/` directory is the documented slop
  pattern; anything else found under a `data/` dir gets migrated into the
  trio or purged. Records PRODUCED BY SERVICES go one level deeper:
  `<node>/data/records/service-records/<node>-<topic>-service-record.json`,
  file names prefixed with the node's short name. That is a LOCATION AND
  NAMING convention only — the record's content is whatever the service
  needs (JSON Schema, JSON-LD, plain JSON, any detail level). A record
  there is data validated against the canonical schema its owning section
  keeps under `data/records/schema/`, and read and written only by that
  section's scripts (live example: each house's
  `data/records/service-records/<node>-enterprise-brand-service-record.json`,
  written by `enterprise-branding-services-section/scripts/write-enterprise-brand.mjs`);
  a brand record exists only for public custody and the five houses, and a
  section's name is its function, never its brand (owner-ruled 2026-09-06).
  The mapping: journals/event streams → `logs/`; dated
  receipts, settlements, attestations, deployments, projections →
  `records/`; runtime trees, caches, reservations, locks, task stores,
  credentials, content-addressed stores → `state/`. Code writing to an
  invented path IS the debt — fix the writer to realize this law, never
  just relocate the files around it (owner-ruled 2026-08-30).
- Repo root stays lean (owner-ruled 2026-08-30): it is the environment we
  develop from, not a workspace. ONE environment entry file
  (`manifest.scm`); never a root `package.json`/lockfile/`node_modules`,
  never a pnpm workspace, never sidecar app directories at root.
- Operational scripts: `scripts/` (2,160 in tree), never `bin/`. No XDG
  paths — no `~/.local/state` style locations for repo concerns.
- Custody: a finding about another section's material is recorded as a
  finding, never fixed en passant.

## Publish gates (local Verdaccio)

All agents must calculate and apply package versions through the shared
`npm-workspace-publication-service` operations: `publish-package` for one
package, `prepare-release-wave` for a family, and `reset-package-versions`
for a Leader-authorized renumbering. Do not invent version numbers, edit
version fields by hand, or substitute raw `npm version` / `npm publish`.
House packages remain `0.X.Y`; breaking changes advance the minor coordinate.
Tests, publication, and deployment do not authorize declaring `1.0.0`.
Only a separate explicit Leader instruction can change that maturity policy.
Use the reset operation's shared map, backups, resume state, and artifact
integrity repair when correcting identities across the registry and consumers.

Before any publish: extract the currently-published tarball from Verdaccio
storage, diff against source, run the package's tests with a fresh install.
Publish only additive/compatible changes with green tests. A breaking diff
means re-pin consumers or stop and record — never publish a major on
momentum. Every publish and refusal goes in a dated receipt.

## Reassess a failed repair

Follow the shared engineering method's reassessment rule: a failed fix calls
for a new diagnosis of the failing system before another change. Inspect the affected contracts and consumers when a failure crosses models, owners, or consumers.
Apply the revised diagnosis and finish the authorized repair. A report of why
the first attempt failed does not discharge the original implementation
request. Redirect affected providers without making the user restart the work.

## Verification channels (from the corpus's own law)

Per the glass-sponge note §16.4
(`engineering-services-section/content/text/documents/articles/notes/2026/08/01/2026-08-01-note-on-the-content-addressed-glass-sponge-semantic-compute-complex.md`):
kinetic proofreading buys error reduction only when a failed candidate
enters an irreversible reject path AND the additional pass uses genuinely
independent information. "Two passes by the same model with the same
prompt and evidence are not two channels... Independence is evidential,
not organizational." So: never present multiple same-model agent reviews
as independent verification; when verifying, vary the evidence base or
method, record WHICH channel caught WHICH defect, and price the
fidelity-throughput trade instead of treating maximum verification as an
unpriced goal.

**Owner-ruled 2026-09-04: verification is a command's exit status, never
a second agent.** Sessions were observed spending their budget on review,
witness, and re-verification agents over other agents' finished lots
("witness theater"). A lot closes on the deterministic gate it names;
the second channel, where one is warranted, is a different deterministic
instrument run by a script, not another model pass. The harness's
important part is routing how work is done first (dispatch-agents,
"Route before you dispatch"), not auditing it afterwards.
